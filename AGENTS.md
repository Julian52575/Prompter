# Agent instructions

First find out which repository you are in: `git remote get-url origin`
(GitHub redirects renamed repositories, so `gh repo view --json nameWithOwner`
gives the current name).

## Working on Julian52575/Big-3-Governed-Template (the template repo)

This repository does not deliver a project. It delivers the governance and
DevOps tooling to build one: the Nix dev shell, the `justfile`, the compose
stack, CI and release workflows, the repository rules and `adapt.py`. The
`frontend/` and `backend/` services are placeholders that exercise that
tooling; keep them minimal. Every change should make sense for any project
created from the template.

Read [README.md](README.md), [CONTRIBUTING.md](CONTRIBUTING.md) and
[README-ADAPT.md](README-ADAPT.md) before changing anything; they are the
source of truth. The hard rules:

- **Conventional Commits** for every commit and PR title:
  `<type>[(scope)][!]: description`, lower-case subject, no trailing period.
- **Signed, signed-off commits**: `git commit -s` with signing configured;
  the `commit-msg` hook rejects anything else.
- **Link the issue** a PR resolves (`Closes #NNN` in the body). Branch from `main`;
  never push to `main`, except until release 1.0.0, which is owner-approved
  to be committed and pushed to `main` directly.
- **Workflows** (`.github/`):
  - pin every action to a full commit SHA with a `# vX.Y.Z` comment that
    matches it (`pin-github-action` does this);
  - least-privilege `permissions:` at workflow level, widened per job only
    where needed;
  - `timeout-minutes` on every job, `step-security/harden-runner` as each
    job's first step, `persist-credentials: false` on every checkout;
  - never expand `${{ … }}` inside `run:` — pass it through `env:`;
  - make a new job mandatory by adding it to `ci-required.needs` in
    `ci.yml`, never by editing `.github/rulesets/main.json`.
  - Run `just lint-workflows` (actionlint, zizmor, schema) before committing.
- **Tooling** comes from the Nix dev shell (`nix develop`).
- **Pin the latest binary release; never compile.** `nix develop` must only
  download. A tool goes in its own `nix/<tool>.nix`, listed in
  `nix/tools.nix`, pinned to its latest **prebuilt** release: the official
  binary when upstream publishes one, else an official package (a PyPI
  wheel), else the newest build on `cache.nixos.org` (nixpkgs-unstable) with
  its version asserted. Never override a nixpkgs package's source: that
  compiles on every machine. Only the Podman stack follows nixpkgs directly.
- **No OS-specific scripts**: new helper scripts are Python 3 (standard
  library only, like `adapt.py`), not shell, so they run on Linux, macOS and
  Windows. `justfile` recipes stay one-liners that call them.
- **Secrets** never go in git. New variables go in `.env.example` with a safe
  placeholder; `change-me-*` values are generated by the shell.
- **Template placeholders** (`OWNER/REPO`, `[INSERT CONTACT METHOD]`,
  `REPLACE_WITH_*`, …) stay as they are; a new one must be handled by
  `adapt.py` and listed in README-ADAPT.md.
- **Comments** stay short and explain why, not what.
- **Read one section, not a whole doc**: `just read-md-section CONTRIBUTING.md#4-releases`.
  `just agent-md-check` reports stale references, duplicated rules and the size of
  this file; `just test-scripts` tests both helpers (`scripts/shared/`).
- Record incidents and their fixes under `docs/troubleshooting/<area>/`
  (see CONTRIBUTING.md).
- AI-assisted commits carry a `Co-Authored-By:` trailer naming the assistant.

## Creating a Prompter template (built-in prompt template)

The user may ask for a new template and want another AI (e.g. ChatGPT) to
write its wording. Then:

1. **Do not write the template yourself.** Write a self-contained prompt for
   the other AI instead, and give it to the user in the chat.
2. Read `frontend/src/core/types.ts` (field types, `Template`),
   `builtins.ts` (style reference) and `render.ts` (how fields and
   `{{placeholders}}` render) first, and embed in the prompt: the types, one
   existing template as style reference, the fields (id, type, defaults), the
   behaviours the preamble/closing must enforce, and "output only the
   TypeScript object". Mention unsupported things: there is no multi-checkbox,
   so model each checkbox as an On/Off `choice` with a `default` and an
   `instruction` per option.
3. **A pasted `Template` object coming back is the request to integrate it**;
   do not ask what to do with it. Review it against `types.ts` and `lint.ts`,
   fix voice and schema problems (hints are shown to the user, so no
   first-person AI wording), then add it to `builtins.ts` and
   `BUILTIN_TEMPLATES`, update the list assertion in `core.test.ts`, add
   render/validation tests in `render.test.ts`, add French labels in
   `ui/i18n.ts`, and run `vitest` and `tsc`. Tell the user what you changed
   from the pasted version.
4. Scripts a template relies on go in `scripts/shared/` (Python, standard
   library only) with their tests in `scripts/shared/tests/`, and each is one row
   in `scripts/shared/README.tsv` (name, purpose, usage, requires, summary). The
   receiver of the prompt has no checkout, so the prompt gives each script's raw
   GitHub URL at the latest release tag (`releases/latest` API), else `main`
   while there is no release, tells the AI to read it before running, and falls
   back to writing its own from the README.tsv row.
5. Commit and push only when asked (see the commit rules above).

## Prompt examples

Store each generated prompt with a real AI output in
`docs/examples/<template_name>-<mode>_.md`, verbatim and each inside a
four-backtick `markdown` fence (the prompt holds its own fences). Sections:
`# Generated Prompt`, then `# AI Output` with `##### <ai_model_used>` above the
raw output.

## Working on a repository created from the template

Follow [README.md](README.md) and [CONTRIBUTING.md](CONTRIBUTING.md); they
describe this project's stack and rules.

When adding a tool to the dev shell, follow the same rule as the template:
**pin its latest binary release in its own `nix/<tool>.nix`; never compile**
(see `nix/tools.nix` and the template section above).

**Tell the user, once per session,** that this AGENTS.md is still the
template's: the section above describes the template repository, not their
project. Suggest they rewrite it for their project, keeping only the rules
that still apply.

**If the repository is not adapted yet** (`./adapt.py --workflow` reports
failures, or template placeholders such as `OWNER/REPO` remain), recommend
letting you guide them through [README-ADAPT.md](README-ADAPT.md). Then follow
it step by step: explain each step, run `adapt.py` with them, and show every
command before running it. Never ask for secret values in the chat; let the
user type them into `adapt.py --gh-vars` themselves.
